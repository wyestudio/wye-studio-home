## 1. 공개 화면 — 무엇이 달라지나

### 1-1. 흐름 비교

```
[ 현재 ]
/contents ─── 회차 카드가 계속 쌓임 ────> /sessions/0829-meeting ──> /apply
              ┌──────────┐┌──────────┐    회차 1건 전용 페이지
              │8/29 오후 ││8/29 저녁 │     (설명은 코드에 하드코딩)
              │  그룹    ││ 소개팅   │
              └──────────┘└──────────┘
              10/5, 10/12, 10/19 … 매주 2장씩 늘어남
              → "이 회차랑 저 회차랑 뭐가 다른데? 설명도 똑같네?"

[ 변경 후 ]
/contents ─── 테마 카드 (테마 수만큼만) ──> /themes/baotalchul ──> /apply
              ┌──────────────┐              테마 소개 + 날짜 선택
              │  바-ㅇ탈출   │              회차가 몇 개든 페이지는 1개
              │  ★★★☆☆      │
              │  3시간 30분  │
              └──────────────┘
```

**핵심 효과**: 회차를 매주 추가해도 **목록 화면과 페이지 수가 늘지 않는다.** 방탈출·공연 예매 사이트의 일반적인 구조이기도 하다.

### 1-2. 라우팅 재편

| 현재 | 변경 후 | 비고 |
|---|---|---|
| `/` | `/` | 홈. Hero 카드가 회차 → **테마** 기준으로 |
| `/contents` | `/contents` | 회차 그리드 → **테마 그리드** |
| `/sessions/[slug]` | **`/themes/[slug]`** | 테마 상세 + 날짜 선택 |
| `/sessions/[slug]/apply` | **`/themes/[slug]/apply?session=<id>`** | 신청 |
| `/sessions/[slug]/opengraph-image` | `/themes/[slug]/opengraph-image` | 테마 단위 OG |
| `/lookup`, `/lookup/result` | 그대로 | 참여내역 조회 |
| `/notice`, `/about`, `/terms`, `/privacy` | 그대로 | |
| — | **`/login`, `/signup`, `/account`** | 휴면 해제([D-06](./06-decisions.md#d-06-로그인-부활--실익-4가지-모두-채택-)) |

#### 특정 날짜 딥링크

마케팅에서 "10/5 회차 바로가기"가 필요하다. **별도 페이지를 만들지 않고 쿼리 파라미터로** 처리한다.

```
/themes/baotalchul?d=2026-10-05   → 테마 페이지에서 해당 날짜가 미리 선택된 상태
```

> 회차마다 페이지를 만들면 **내용이 거의 같은 페이지가 매주 2개씩 늘어나** 검색엔진이 중복으로 판단한다. 페이지를 하나로 모으면 그 URL에 SEO 점수가 누적된다.

#### 기존 URL 처리

```
/sessions/0829-meeting  ─┐
/sessions/0829-dating   ─┼─> 301 → /themes/baotalchul
/sessions/<UUID>        ─┘   (이미 있는 UUID→slug 리다이렉트 로직 확장)
```

`next.config.ts`의 **UTM 짧은 링크 13개 중 6개가 `0829-*` 고정**이다(`/ig-dating.go`, `/yt-meeting.go` 등). 전부 `/themes/baotalchul`로 갱신한다. 짧은 링크 자체는 이미 배포된 SNS 프로필에 박혀 있으므로 **주소는 유지하고 목적지만 바꾼다.**

`sitemap.ts`도 회차 목록 → 테마 목록으로 교체한다.

### 1-3. 테마 상세 페이지 (`/themes/[slug]`)

```
┌────────────────────────────────────────────────────┐
│  [히어로 이미지]                                    │
│  바-ㅇ탈출                        난이도 ★★★☆☆     │
│  3시간 30분 · 서울 신림역 인근 · 55,000원 (79,000)  │
├────────────────────────────────────────────────────┤
│  ▸ 이런 분께 추천        content.for_you           │
│  ▸ 이렇게 진행돼요       content.steps             │
│  ▸ 타임테이블            content.timetable ⭐      │
│  ▸ 주의사항              content.precautions       │
├────────────────────────────────────────────────────┤
│  📅 날짜 선택                                       │
│                                                     │
│   ┌─────────┐ ┌─────────┐ ┌─────────┐             │
│   │ 10/5(토)│ │10/12(토)│ │10/19(토)│             │
│   │  14:00  │ │  14:00  │ │  14:00  │             │
│   │ 잔여 12 │ │  마감   │ │ 잔여 30 │             │
│   └─────────┘ └─────────┘ └─────────┘             │
│                                                     │
│              [ 신청하기 ]                           │
└────────────────────────────────────────────────────┘
```

- **타임테이블은 선택한 날짜의 시작 시각 기준으로 다시 그려진다.** `offset_min` 방식이라 14시 회차를 고르면 `14:00 / 14:40 / …`, 19시 회차를 고르면 `19:00 / 19:40 / …`로 자동 계산된다([07 §4-2](./07-architecture-domain-and-data.md)).
- **잔여석 판정 기준은 현행 유지** — `paid_confirmed_count`(입금 확인까지 끝난 인원). 확정만 되고 미입금인 자리를 마감으로 세면 실제로는 빈자리를 막게 된다. 이건 실전에서 나온 개선이라 반드시 계승한다.
- 날짜를 고르기 전에는 **[신청하기]가 비활성**이다.

### 1-4. 홈 / `/contents`

- 홈 히어로의 스크롤텔링(`ScrollStage`)·마스코트·별 배경은 **그대로 유지**한다. 브랜드 자산이다.
- `SessionShowcase` / `ContentsSessionShowcase`가 회차 카드를 그리던 것을 **테마 카드**로 교체한다.
- `SessionCard`의 `"8/29 pre-open 한정 할인가"` 하드코딩 문구를 제거하고, 테마의 `price_krw` / `original_price_krw` 관계로 할인 표시를 일반화한다.

## 2. 신청 폼

### 2-1. 사라지는 분기

현재 `'소개팅'` 리터럴을 참조하는 파일이 **19개**, `isDatingTheme()` 호출이 **37곳**이다. 신청 플로우에서 아래가 전부 사라진다.

| 제거 | 이유 |
|---|---|
| 소개팅 = 1인 강제 | 형식 구분 자체가 없어짐 |
| 성별 필수 선택 | 선택 입력으로 완화([D-04](./06-decisions.md#d-04-성별--선택-입력으로-전환-)) |
| 테마별 출생년도 안내 문구 2종 | 만 14세 단일 규칙([D-03](./06-decisions.md#d-03-나이-제한--출생연도-기준-보수적-판정-)) |
| 소개팅 전용 안내 불릿(`ApplyNotices`) | 음주 안내 등 |
| 성별 잔여석 뱃지 | 성별 정원 폐지 |

**모든 신청이 그룹 신청 가능**해진다(1명도 그룹 크기 1일 뿐).

### 2-2. ⭐ 입금자명 입력란 — 이 설계의 성패가 달린 부분

[D-07a](./06-decisions.md#d-07a-입금-확인-자동화--오픈뱅킹-api-방식-)에서 **입금액 + 입금자명**으로 매칭하기로 확정했다. 즉 **고객이 입력한 이름과 실제 입금자명이 다르면 자동 확인이 안 된다.** 이걸 고객이 알게 하는 것이 UI의 책임이다.

```
┌──────────────────────────────────────────────┐
│  입금자명 *                                   │
│  ┌────────────────────────────────────────┐  │
│  │ 홍길동                                  │  │
│  └────────────────────────────────────────┘  │
│  ⚠️ 실제로 입금하실 분의 성함과 정확히        │
│     일치해야 자동으로 확인됩니다.             │
│     가족·지인 명의로 입금하시는 경우          │
│     그분의 성함을 적어주세요.                 │
└──────────────────────────────────────────────┘
```

- 도움말이 아니라 **경고 스타일**로 입력란 바로 아래 상시 노출한다(접었다 펴는 형태 금지).
- 신청자 이름과 입금자명이 **다를 때** 한 번 더 확인시킨다 — "입금자명이 신청자 성함과 다릅니다. 맞습니까?"
- 회사명·별칭 입금이 잦다면 운영 데이터를 보고 문구를 조정한다(`sms_templates`처럼 문구를 DB로 뺄지는 09에서 판단).

### 2-3. 신청 완료 화면

입금 안내가 **화면의 주인공**이 되어야 한다. 현재는 간이 버전만 있다.

```
┌────────────────────────────────────────────────────┐
│  ✅ 신청이 접수되었습니다                           │
│  접수번호  184729                                   │
├────────────────────────────────────────────────────┤
│  아래 계좌로 입금해주세요                           │
│                                                     │
│    카카오뱅크  3333-05-2843942                      │
│    예금주      우주이스케이프                       │
│                                                     │
│    입금액      110,000원                            │
│    입금자명    홍길동      ← ⚠️ 이 이름으로 입금    │
│                                                     │
│  ⚠️ 입금자명이 다르면 자동 확인이 되지 않아          │
│     처리가 늦어질 수 있습니다.                      │
│  ⏱ 30분 내 미입금 시 자동 취소됩니다.               │
│  ⏱ 입금 확인까지 최대 10분 정도 걸릴 수 있습니다.   │
└────────────────────────────────────────────────────┘
```

- **계좌 정보는 `site_settings`에서 읽는다.** 현재 `src/lib/bankAccount.ts`에 개인 명의 계좌가 하드코딩돼 있어, 계좌가 바뀌면 배포가 필요하다.
- **"입금 확인까지 최대 N분"** 문구가 필요한 이유: 오픈뱅킹은 webhook이 아니라 **폴링**이라 실시간이 아니다([07 §5-2](./07-architecture-domain-and-data.md)). 이 안내가 없으면 문의가 늘어난다.
- 문자1(신청확인) 템플릿에도 같은 내용을 반영한다.

### 2-4. 나이 안내

```
출생연도 *   [ 2001 ▾ ]
   만 14세 이상만 참여하실 수 있습니다.
```

선택지는 **현재 연도 기준으로 자동 생성**한다(`올해 - 15` 이하). 상한은 두지 않는다. 연도를 코드나 DB에 상수로 박지 않는다 — 해가 바뀌면 자동으로 넓어져야 한다.

## 3. 어드민 재설계

[D-09](./06-decisions.md#d-09-어드민-범위--쇼핑몰급-전체-)에서 **쇼핑몰급 전체**로 확정했다. 다만 만드는 순서는 09 로드맵에서 단계화한다.

### 3-1. 지금의 문제

```
[ 현재 /admin ]
관리자 대시보드          [협찬][후기페이백][문자포맷][분석][로그아웃]
┌──────────────────────────────────────┐
│ 그룹 바-ㅇ탈출              상태: 마감│
│ 2026.08.29 13:00          [링크 복사] │
└──────────────────────────────────────┘
```

**세션 목록 화면 하나 + 상단 버튼 4개가 전부**다. 분류가 없고, 회차 등록은 SQL Editor에서 직접 해야 한다.

### 3-2. 정보 구조 (IA)

좌측 사이드바로 영역을 나눈다. `admin.wouldyouescape.com` 서브도메인 분리는 **유지**한다(잘 되어 있다).

```
📊 대시보드                    오늘 할 일 + 지표

🎭 상품
   ├ 테마                     CRUD, 콘텐츠 편집, 노출 제어
   └ 장소                     CRUD (현재 SQL 전용)

📅 일정
   └ 회차                     CRUD, 일괄 생성, 마감/재오픈/비활성화

🧾 주문
   ├ 신청 목록                전체 검색·필터·정렬  ⭐신규
   └ 미매칭 입금              자동 매칭 실패 건 처리  ⭐⭐ 매일 사용

💰 정산
   ├ 매출                     기간별 매출·환불
   └ 환불                     환불 대기·완료 처리

👥 고객
   ├ 고객 목록                참여 이력, 노쇼·블랙리스트
   └ 포인트                   적립·차감 이력

📝 콘텐츠
   ├ 공지                     현재 코드 하드코딩
   └ FAQ                      현재 코드 하드코딩

🔔 알림
   ├ 문자 템플릿              (기존 유지)
   └ 발송 이력                실패 재시도  ⭐신규

📣 마케팅
   ├ 협찬 신청                (기존 유지)
   ├ 후기 페이백              (기존 유지)
   └ 유입 분석                (기존 GA4 화면 유지)

⚙️ 설정
   ├ 운영자                   계정·역할
   ├ 사이트 설정              입금 계좌, 미입금 취소 시간 등
   └ 감사 로그                누가 무엇을 했나
```

### 3-3. 대시보드 — "오늘 할 일"이 먼저

지표보다 **처리 대기 항목**이 위에 온다. 매주 운영에서 실제로 필요한 건 "지금 내가 뭘 해야 하나"다.

```
┌─────────────── 처리 대기 ───────────────┐
│  🔴 미매칭 입금        3건   [처리하기]  │
│  🟡 입금 확인 전       5건   [보기]      │
│  🟡 환불 대기          2건   [처리하기]  │
│  🔵 대기자             4명   [보기]      │
└──────────────────────────────────────────┘

┌─────────────── 이번 주 ─────────────────┐
│  신청 32건 · 확정 28명 · 매출 1,540,000원│
│  다가오는 회차: 10/5(토) 14:00  잔여 12  │
└──────────────────────────────────────────┘
```

### 3-4. ⭐⭐ 미매칭 입금 화면 — 가장 중요한 신규 화면

자동 매칭이 실패한 입금을 사람이 빠르게 처리하는 곳이다. **이 화면 없이는 오픈뱅킹 방식이 성립하지 않는다.**

```
┌─ 미매칭 입금 (3) ────────────────────────────────────────────┐
│                                                               │
│ ┌───────────────────────┐  ┌──────────────────────────────┐ │
│ │ 10/03 14:22           │  │ 후보 신청                     │ │
│ │ 110,000원             │  │                               │ │
│ │ 입금자  김민수         │  │ ○ 접수 184729 · 김민수        │ │
│ │                       │  │   110,000원 · 2명 · 10/5      │ │
│ │ 매칭 실패 사유:        │  │   ⚠️ 동명이인 2건             │ │
│ │ 같은 조건 신청 2건     │  │                               │ │
│ │                       │  │ ○ 접수 184801 · 김민수        │ │
│ │ [무시(우리 입금 아님)] │  │   110,000원 · 2명 · 10/12     │ │
│ └───────────────────────┘  │                               │ │
│                             │  [ 선택한 신청에 연결 ]        │ │
│                             └──────────────────────────────┘ │
└───────────────────────────────────────────────────────────────┘
```

**후보 추천 규칙** (자동 매칭이 실패한 뒤 사람에게 보여줄 순서):

1. 금액 일치 + 이름 일치 → 여러 건이면 전부 (모호 케이스)
2. 금액 일치, 이름 불일치 → 미입금 건 중 금액이 같은 것
3. 이름 일치, 금액 불일치 → 오입력·분할입금 가능성
4. 금액 근사(±10,000원) → 오입력 가능성

**액션**:

| 액션 | 결과 |
|---|---|
| **연결** | `payment_status='confirmed'`, `matched_by='manual'`, **문자2(입금확인) 발송**, 감사로그 기록 |
| **무시** | `ignored_at` 기록 + 사유. 우리 매출이 아닌 입금 |
| **부분 처리** | 분할 입금 등 예외. 메모를 남기고 수동 확정 |

> 연결은 **되돌리기 어려운 액션**(문자가 나간다)이므로 확인 다이얼로그와 감사로그가 필수다. 기존 어드민의 `getDeactivatePreview` / `getReminderPreview`처럼 **실행 전 미리보기**를 보여주는 패턴이 이미 있으니 계승한다.

### 3-5. 신청 목록 화면

현재는 `/admin/sessions/[id]` 안에서만 신청을 볼 수 있다. **회차가 매주 쌓이면 전체 목록이 필수**다.

```
검색: [접수번호·이름·전화번호]   회차: [전체 ▾]  상태: [전체 ▾]  기간: [최근 30일 ▾]

접수번호 │ 신청자   │ 인원 │ 회차        │ 상태   │ 입금   │ 금액
184729   │ 홍길동   │  2   │ 10/5(토)    │ 확정   │ 완료   │ 110,000
184801   │ 김민수   │  1   │ 10/12(토)   │ 대기   │ 대기   │  55,000
```

- 전화번호·이름은 암호화돼 있어 **`admin_attendee_view`(복호화 뷰) 기준으로 검색**한다. 대량 데이터에서 느려지면 검색용 해시 컬럼을 추가한다.
- 정렬·페이지네이션 필수. 현재는 전건 로드다.

### 3-6. 테마 / 회차 관리

**테마 편집**은 `content` JSONB의 4개 블록(추천 대상·진행 방식·타임테이블·주의사항)을 **블록 단위로 추가/삭제/순서변경**하는 편집기가 필요하다. `/admin/sms-templates`의 `SmsTemplateEditor` + `PlaceholderHints` 패턴을 확장하면 된다.

> ⚠️ JSONB는 DB가 구조를 검증해주지 않는다([07 §4-2](./07-architecture-domain-and-data.md)). **저장 시 애플리케이션 레벨 스키마 검증이 필수**다.

**회차 등록**은 이 프로젝트의 G1(매주 개발자 없이 운영)을 직접 푸는 화면이다.

```
회차 추가
  테마     [ 바-ㅇ탈출 ▾ ]
  날짜     [ 2026-10-05 ]
  시작시각 [ 14:00 ]
  종료시각 (자동: 17:30 — 테마 소요시간 210분)

  ▸ 고급 (가격·정원·장소 덮어쓰기)   ← 접혀 있음, 비워두면 테마 값 사용

  [ 반복 생성 ] 매주 토요일 · 4주치 한 번에
```

**반복 생성**이 정기 운영의 핵심이다. 매주 손으로 만들 필요가 없어야 한다.

### 3-7. 콘텐츠 관리 (공지 / FAQ)

현재 `NoticeSection.tsx` / `FaqSection.tsx`에 배열로 하드코딩돼 있어 문구 하나 고치는 데 배포가 필요하다.

> ⚠️ **FAQ는 그대로 옮길 수 없다.** 현재 답변 안에 `<br/>`, `<span className="font-semibold">` 같은 **JSX가 섞여 있다.** 서식 표현 방식(마크다운 / 제한적 HTML / 블록)을 먼저 정해야 한다 — 09 로드맵의 선행 결정 항목.

## 4. 어드민 인증 · 권한 · 감사로그

### 4-1. 현재

`ADMIN_PASSWORD` **공유 비밀번호 1개** → HMAC 서명 쿠키(24시간). 계정 개념이 없어 **"누가 무엇을 했는지" 기록이 원천적으로 불가능**하다.

### 4-2. 제안 — Supabase Auth + 역할 테이블

```
admin.wouldyouescape.com
        │
        ├─ proxy.ts 가 admin_auth 확인 (현행 구조 유지)
        │
        └─ 인증: Supabase Auth (이메일 + 비밀번호)
           권한: admin_users 테이블로 user_id → role 매핑
```

```sql
create table admin_users (
  user_id    uuid primary key references auth.users(id),
  name       text not null,
  role       text not null check (role in ('owner','staff')),
  is_active  boolean not null default true,
  created_at timestamptz not null default now()
);
```

| 역할 | 권한 |
|---|---|
| `owner` | 전체. 운영자 관리, 사이트 설정, 테마·회차 삭제 |
| `staff` | 일상 운영. 입금 처리, 신청 관리, 문자 발송. **설정·삭제 불가** |

**이 방식을 고르는 이유**:
- 로그인 시스템을 어차피 부활시키므로([D-06](./06-decisions.md#d-06-로그인-부활--실익-4가지-모두-채택-)) **인증 기반이 이미 있다.** Supabase Auth에 Email provider가 켜져 있고 Resend SMTP도 연결돼 있다.
- 감사로그의 `actor`가 **실명이 된다.** 공유 비밀번호로는 불가능하다.
- 사람이 나가면 그 계정만 비활성화하면 된다. 지금은 비밀번호를 바꾸고 전원에게 다시 공유해야 한다.

> ⚠️ **고객 계정과 운영자 계정이 같은 `auth.users`를 공유한다.** `admin_users`에 행이 있는 사용자만 어드민에 들어갈 수 있게 하고, 어드민 판정을 **반드시 서버에서** 한다. 클라이언트 판정은 신뢰할 수 없다.

### 4-3. 감사로그 — 되돌리기 어려운 것부터

```sql
create table audit_logs (
  id          bigserial primary key,
  actor_id    uuid references auth.users(id),
  actor_name  text not null,          -- 스냅샷 (계정이 삭제돼도 기록은 남아야 함)
  action      text not null,          -- 'application.cancel'
  target_type text not null,          -- 'application'
  target_id   text not null,
  summary     text,                   -- '접수 184729 취소 (미입금)'
  detail      jsonb,                  -- 변경 전/후
  created_at  timestamptz not null default now()
);
```

**최소 기록 대상** (전부 되돌리기 어렵거나 고객에게 문자가 나간다):

| action | 비고 |
|---|---|
| `payment.confirm` | 입금 확인 (자동/수동 구분) |
| `payment.match_manual` | 미매칭 입금 수동 연결 |
| `application.cancel` | 신청 취소 → 문자4 |
| `application.promote` | 대기 → 확정 → 문자6 |
| `application.manual_create` / `update` | 수동 등록·수정 |
| `refund.complete` | 환불 완료 |
| `session.deactivate` | 회차 비활성화 → 전원 일괄 취소 + 문자7 |
| `theme.update` / `settings.update` | 가격·계좌 변경 |

> 2026-08-14 장애(프로덕션 함수 오삭제로 서비스 마비)의 교훈이 "무엇이 언제 바뀌었는지 알 수 없었다"였다. 감사로그는 그 재발 시 **원인 추적을 가능하게 하는 최소 장치**다.
