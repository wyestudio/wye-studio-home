## D-01. 테마 / 회차 2단 구조로 분리 🟢

**결정일**: 2026-09-08

### 결정

`sessions` 한 덩어리를 **테마(상품)** 와 **회차(일정)** 두 개로 분리한다.

| | 담는 것 |
|---|---|
| **테마** | 소개글, 이미지, 난이도, 진행방식, **가격, 정원, 소요시간, 장소** |
| **회차** | **날짜·시간**, 모집 상태(open/closed/cancelled), 신청 데이터 연결 |

즉 **테마가 마스터 정보를 전부 갖고, 회차는 날짜만 늘어난다.**

### 이유 (사용자 원문 요지)

- 장소·가격·정원·소요시간이 **이미 확정**되어 매 회차 달라지지 않는다.
- 지금처럼 회차마다 카드가 쌓이면 **홈페이지가 지저분해지고**, 사용자 입장에서 *"이 회차랑 저 회차랑 뭐가 다른데? 상세 설명도 똑같네?"* 가 된다.
- 일반적인 방탈출 예매 사이트 / 뮤지컬 예매 사이트처럼 **테마를 고르고 → 들어가서 날짜를 선택하고 → 신청**하는 흐름으로 가고 싶다.

### 함께 따라오는 화면 구조 변경

| | 현재 | 변경 후 |
|---|---|---|
| 목록 | `/contents` → **회차** 카드가 계속 쌓임 | `/contents` → **테마** 카드 (테마 수만큼만) |
| 상세 | `/sessions/[slug]` — 회차 1건 상세 | 테마 상세 + **그 안에서 날짜(회차) 선택** |
| 신청 | `/sessions/[slug]/apply` | 테마 + 선택한 날짜 조합으로 신청 |

→ 회차가 늘어나도 **목록 화면은 그대로**다. 이게 이번 구조 변경의 핵심 효과다.

### 구현 시 유의

- **회차별 덮어쓰기(override)는 지금 넣지 않는다.** 다만 나중에 "연말 특별 회차만 가격 다르게" 같은 요구가 생길 수 있으므로, 회차 테이블에 **nullable override 컬럼**을 두는 형태로 확장하면 기존 데이터를 건드리지 않고 추가할 수 있다. 설계 단계에서 이 확장 여지만 남겨둘 것.
- **장소**: 현재 `session_venues`가 회차별 1:1 비공개 테이블이다. 장소가 확정되었으므로 테마로 올라가지만, 대관 장소가 바뀔 가능성은 있으므로 위와 같은 override 여지를 남긴다. (공개용 대략 위치 `venue_area` / 비공개 정확 주소 `venue_address` 분리는 유지 — 전날안내 문자가 정확 주소를 쓴다.)
- **소요시간**: 테마에 소요시간을 두면 회차의 `end_at`을 `start_at + 소요시간`으로 자동 계산할 수 있다. 지금은 둘 다 수동 입력이라 정합성 보장 장치가 없다.
- `sessions.slot`의 CHECK(`afternoon`/`evening`)은 이 구조에서 재검토 대상 — 날짜·시간이 회차의 본질이 되므로 슬롯 열거형이 필요한지 다시 판단.

## D-02. 재참여 정책 — 같은 테마만 1회 제한 🟢

**결정일**: 2026-09-08

### 결정

**같은 테마는 1인 1회만.** 다른 테마는 자유롭게 신청 가능.

### 이유

- 방탈출은 **문제를 이미 아는 사람이 다시 오면 게임이 성립하지 않는다** — 본인 재미도, 같은 팀 다른 참가자의 경험도 깨진다.
- 동시에 **새 테마가 나오면 다시 올 수 있으므로 단골이 생긴다.** 현행처럼 평생 1회로 막히지 않는다.

### 현행 대비 변경점

| | 현재 | 변경 후 |
|---|---|---|
| 판정 단위 | `sessions.content_group` (컨텐츠 그룹) | **테마 단위** |
| 실질 효과 | 바-ㅇ탈출 참여자는 **영구히 재신청 불가** | 바-ㅇ탈출은 1회, 새 테마는 신청 가능 |

### 구현 시 유의

- `submit_application()`의 배타 체크를 `content_group` 일치 → **`theme_id` 일치**로 바꾼다.
- 취소된 신청은 계속 카운트에서 제외한다 (현행 `status <> 'cancelled'` 유지). 취소하고 다시 신청하는 정상 케이스를 막으면 안 된다.
- 판정 키는 현재 `application_attendees.phone_hash`(HMAC)다. 로그인이 부활하면 계정 기준과 어떻게 합칠지가 [D-06](#d-06-로그인-부활--실익-4가지-모두-채택-)과 연결된다.
- ✅ **기존 데이터 이관은 1:1로 대응된다.** 기존 두 회차가 같은 `content_group = 'baotalchul'`이었고, 이것이 곧 「바-ㅇ탈출」 테마 하나다. 따라서 `content_group` → `theme_id` 치환만으로 **배타 관계가 그대로 보존**되며 실질 동작은 바뀌지 않는다. 상세는 [D-05](#d-05-소개팅-기존-데이터--그대로-보존-) 참고.

## D-03. 나이 제한 — 출생연도 기준 보수적 판정 🟢

**결정일**: 2026-09-08

### 결정

**출생연도만 계속 수집**하고, **만 14세가 확실한 사람만** 통과시킨다.

```
허용 조건:  birth_year <= (올해) - 15
2026년이면: 2011년생까지 허용, 2012년생부터 차단
```

생일이 지난 2012년생(만 14세) 일부가 함께 차단되지만, **만 13세가 통과하는 일은 발생하지 않는다.**

### 이유

- 만 14세 제한의 목적은 **개인정보보호법상 "만 14세 미만은 법정대리인 동의 필요"라는 절차를 만들지 않기 위함**이다. 따라서 판정이 느슨해서 만 13세가 섞이면 제한 자체가 무의미해진다.
- 생년월일까지 받으면 정확하지만, **암호화 대상 개인정보가 하나 더 늘어난다.** 최소수집 원칙에서 손해이고 폼 입력도 늘어난다.
- 주 고객층이 20~30대인 파티형 방탈출이라 **보수적 판정으로 놓치는 인원이 사실상 없다.**

### 구현 시 유의 (중요)

- ⚠️ **연도를 상수로 박지 말 것.** 현재 DB CHECK 제약이 `birth_year between 1987 and 2007`처럼 **숫자가 고정**돼 있어 해가 바뀔 때마다 사람이 직접 고쳐야 한다. `EXTRACT(YEAR FROM now()) - 15` 처럼 **현재 연도 기준 자동 계산**으로 바꾼다.
- **상한(하한 연도) 제거**: 기존 `>= 1987` 같은 상한 나이 제한은 없앤다 (사용자 요청: "만 14세 제한만 두기").
- 테마별 출생연도 분기(소개팅 1990~2001 / 그룹 1987~2007)는 **전부 제거**하고 단일 규칙으로 통일한다.
- **DB 변경 순서 주의**: CLAUDE.md v40 기록의 교훈대로 **CHECK 제약을 먼저 넓힌 뒤 함수를 교체**한다. 반대 순서면 넓어진 함수가 좁은 제약에 막히는 순간이 생긴다.
- 프론트 상수(`src/lib/eligibility.ts`)·안내 문구·약관도 함께 갱신한다.

## D-04. 성별 — 선택 입력으로 전환 🟢

**결정일**: 2026-09-08

### 결정

성별을 **필수 → 선택 입력**으로 낮춘다. (컬럼 유지, `nullable`)

### 이유

- 성별을 필수로 받던 유일한 목적은 **소개팅 회차의 성비 정원 관리**였다. 소개팅을 없애면 이 목적이 사라진다.
- 개인정보는 목적이 있을 때만 수집하는 것이 원칙이므로 필수 유지는 근거가 약하다. 다만 완전히 버리기보다 **참고 통계용으로 선택 수집**한다.

### 구현 시 유의

- ⚠️ **팀 배정에 성별을 활용하려면 빈칸 처리 규칙이 필요하다.** 선택 입력이라 값이 없는 참여자가 생기므로, 성비를 맞추는 로직을 만들 경우 미입력자를 어떻게 배치할지 정해야 한다. (운영상 성비를 안 맞춘다면 무관)
- `application_attendees.gender`는 이미 `nullable`이므로 **컬럼 변경은 불필요**하다. 바꿔야 할 것은 `submit_application()`의 **"모든 참여자의 성별을 선택해주세요" 필수 검증**과 신청 폼 UI다.
- `get_session_stats()`의 성별 카운트 6종은 소개팅 정원 관리용이었다. 통계 용도로 남길지, 정리할지는 어드민 설계 시 함께 판단한다.
- 개인정보처리방침의 수집 항목·목적 기재를 함께 수정한다.

## D-05. 소개팅 기존 데이터 — 그대로 보존 🟢

**결정일**: 2026-09-08

### 결정

소개팅 회차의 실고객 데이터 **34건을 삭제하지 않고 운영 DB에 보존**한다. 새 구조에서 **"지난 테마"** 로 편입해 조회만 가능하게 한다.

| 보존 대상 | 건수 |
|---|---:|
| 확정·입금완료 | 19 |
| 확정·미입금 | 1 |
| 대기 | 1 |
| 취소 | 13 |
| **신청 합계** | **34** |
| 협찬 신청(소개팅) | 2 |

### 이유

- 실제 참여한 고객이 `/lookup`에서 **본인 참여 이력을 계속 조회할 수 있어야** 한다.
- 프리오픈 성과 통계(취소율, 성비, 재신청률)를 나중에 되돌아볼 근거가 된다.
- **현재 DB에 백업이 전혀 없다**(Supabase Free). 되돌릴 수 없는 삭제는 이 상황에서 특히 위험하다 — 이 프로젝트는 이미 2026-08-14에 프로덕션 오삭제로 서비스가 마비된 전력이 있다.

### ⭐ 정정 (2026-09-08) — 소개팅과 그룹은 **같은 테마**다

초안에서 담당자(Claude)가 "소개팅을 별도 테마로 분리해야 한다"고 적었으나 **잘못된 판단이었다. 사용자 정정에 따라 아래가 확정이다.**

> **기존 두 회차(`0829-meeting` / `0829-dating`)는 모두 같은 「바-ㅇ탈출」 테마로 진행됐다.**
> 동일한 테마·동일한 문제이고 **타임 구성(진행 형식)만 달랐다.** 실제로 `FaqSection.tsx`에도
> *"동일한 테마, 동일한 문제로 구성되어 있고 그 외 타임 구성이 달라요"* 라고 명시돼 있다.

따라서:

- 과거 회차 2건 모두 **하나의 활성 테마 「바-ㅇ탈출」에 소속**시킨다. 비활성/별도 테마로 분리하지 않는다.
- **의도한 동작**: 앞으로 바-ㅇ탈출을 신청하는 사람은, 기존에 **소개팅이든 그룹이든 하나라도 참여했으면 신청할 수 없다.** D-02(같은 테마 1회 제한)가 정확히 이 결과를 만든다.
- 소개팅/그룹은 테마가 아니라 **회차의 진행 형식** 구분이었다. 소개팅 형식을 없애면 앞으로는 형식이 하나만 남는다.

### 마이그레이션이 오히려 단순해진다

기존 `sessions.content_group = 'baotalchul'`이 **이미 "같은 컨텐츠는 1회"** 라는 뜻이었으므로, 새 구조의 `theme_id`와 **1:1로 대응**한다.

```
content_group = 'baotalchul'   →   theme = 「바-ㅇ탈출」
```

→ 재참여 배타 판정의 **실질 동작이 바뀌지 않는다.** 판정 키만 `content_group`(문자열) → `theme_id`(외래키)로 정규화하는 것이고, 기존 신청 58건의 배타 관계가 그대로 보존된다.

### 구현 시 유의

- 테마에 **`is_active` / 노출 여부 플래그**는 여전히 필요하다 — 향후 운영을 종료한 테마를 목록에서 내리되 `/lookup` 조회와 어드민에서는 계속 보이게 하기 위함. 다만 **바-ㅇ탈출은 활성 상태를 유지**한다.
- **회차의 "진행 형식"(그룹/소개팅) 구분을 어떻게 남길 것인가**: 신규 회차는 형식이 하나뿐이지만, 과거 회차 2건은 형식이 달랐고 `/lookup`에서 고객에게 그대로 보여야 한다. 회차의 표시용 라벨로 격하하거나 과거 회차에만 값이 있는 선택 컬럼으로 남긴다. **신규 신청 로직에서는 분기하지 않는다.**
- 성별 정원 컬럼 6종(`capacity_*_male/female`, `male_closed`, `female_closed`)은 **과거 회차 재현을 위해 남길지, 통계만 남기고 컬럼은 정리할지** 스키마 설계 시 판단한다. 신규 신청 로직에서는 더 이상 쓰지 않는다.
- `review_payback_applications.session_slug`가 `'0829-dating'`을 문자열로 참조 중이다. 슬러그 체계가 바뀌면 이 참조가 깨지지 않도록 처리한다.

## D-06. 로그인 부활 — 실익 4가지 모두 채택 🟢

**결정일**: 2026-09-08

### 결정

로그인을 부활시키되 **비회원 신청은 계속 지원**한다(사용자 요청: "비회원인 상태에서도 신청할 수 있도록 유연하게").
로그인 사용자가 얻는 실익은 다음 4가지 **전부**:

| # | 실익 | 필요한 구조 | 난이도 |
|---|---|---|---|
| 1 | **재신청 시 자동입력** — 이름·전화번호·출생연도 재입력 불필요 | 계정 ↔ 신청 연결만 있으면 됨 | 낮음 |
| 2 | **참여 이력 보기** — 접수번호 없이 전체 이력 조회 | 계정 ↔ 신청 연결만 있으면 됨 | 낮음 |
| 3 | **후기·리뷰 연결** — 후기 페이백 신청을 계정에 귀속 | `review_payback_applications`에 계정 연결 | 중간 |
| 4 | **단골 혜택·포인트** — 재방문 할인, 포인트, 추천인 | **누적 참여 횟수 + 포인트 원장이 새로 필요** | 높음 |

> 1·2번은 계정을 붙이는 것만으로 바로 되고, 4번은 **지금 존재하지 않는 구조**(적립·차감 이력, 잔액, 만료 규칙)를 새로 만들어야 한다. 구현은 단계를 나눠 1·2 → 3 → 4 순서를 권한다.

### 현재 상태 (활용 가능한 자산)

- 로그인·회원가입·계정연결 화면과 카카오/네이버 OAuth 라우트가 **삭제되지 않고 전부 남아 있다.**
- Supabase Auth에 **Email·Kakao provider가 이미 켜져 있고**, Resend 커스텀 SMTP도 연결돼 있다.
- `profiles` / `kakao_links` / `naver_links` 테이블 존재 (전부 0행).

### 결정적 갭

⚠️ **`applications`에 계정을 가리키는 컬럼이 없다.** 계정과 신청을 잇는 연결고리가 아예 없는 상태다.
현재 사람을 식별하는 유일한 키는 `application_attendees.phone_hash`(HMAC)다.

### 구현 시 유의

- `applications`에 **nullable `user_id`** 를 추가한다. 비회원 신청은 `null`로 남고, 로그인 신청만 채워진다 — 이래야 비회원 플로우가 그대로 유지된다.
- **비회원 신청의 사후 귀속(중요·보안)**: 로그인 후 "내 전화번호로 된 과거 신청"을 계정에 연결할 때, **전화번호만으로 자동 귀속하면 남의 전화번호를 아는 사람이 그 신청을 가져갈 수 있다.** 반드시 소유 증명을 거친다 — 최소한 **전화번호 + 접수번호** 조합(현행 `/lookup`과 동일 기준), 또는 SMS OTP. → 기본 방침: **접수번호 확인 방식**으로 간다. 이견 있으면 재논의.
- **`profiles`는 평문, `application_attendees`는 암호화**로 저장 방식이 갈려 있다. 계정이 살아나면 같은 사람의 정보가 두 방식으로 공존하므로 **통일 방침이 필요**하다.
- **네이버**: 현재 자체 OAuth 라우트로 구현돼 있으나, 네이버가 표준 OIDC 지원을 시작한 것으로 기록돼 있다. 착수 시 `https://nid.naver.com/.well-known/openid-configuration`을 **다시 조회해 현행 확인**하고, 가능하면 Supabase Custom OIDC로 단순화한다.
- **테스트 환경에 카카오/네이버 키가 없다** — 테스트 Vercel 프로젝트에 `KAKAO_*` / `NAVER_*` 추가 필요.
- **`disable_signup`이 현재 `false`** 라 가입 API가 열려 있다. 부활 전까지 닫아두거나, 부활과 동시에 rate limit·봇 방어를 함께 적용한다.

## D-08. DB 백업 — 자체 백업 스크립트 🟢

**결정일**: 2026-09-08

### 결정

**Supabase Pro로 전환하지 않고, 자체 백업 스크립트를 만든다.**
(참고: Supabase Pro는 월 $25부터 / 매일 백업 7일 보관, Free는 백업 없음 — 2026-09-08 공식 페이지 확인)

### ✅ 구현 완료 (2026-09-08)

- 워크플로: **`.github/workflows/db-backup.yml`** (매일 18:30 UTC = 03:30 KST)
- 복구 절차: **[RUNBOOK-db-backup-restore.md](./RUNBOOK-db-backup-restore.md)**
- ⏳ **담당자 조치 필요**: GitHub Secrets 3개 등록 (`SUPABASE_DB_URL`, `BACKUP_ENCRYPTION_PASSPHRASE`, `SLACK_WEBHOOK_URL`) + Vault PII 키 별도 보관. 등록 전까지 백업은 실패한다. 절차는 런북 §1.

### 구현 시 확인된 함정 2가지

1. **Direct connection 을 쓰면 아예 접속이 안 된다.** Free 플랜의 direct 엔드포인트(`db.<ref>.supabase.co:5432`)는 **IPv6 전용**이고 **GitHub Actions 러너는 IPv4 전용**이다(Supabase 공식 문서가 GitHub Actions 를 IPv6 미지원 플랫폼으로 명시). → **Session Pooler**(`aws-<region>.pooler.supabase.com:5432`, 전 요금제 IPv4)를 써야 한다.
2. **public 저장소의 Actions artifact 는 사실상 공개다.** GitHub 문서상 artifact 다운로드에는 "read access to the repository"만 필요한데, public 저장소는 모두가 read 권한을 가진다. → **GPG AES256 대칭키 암호화가 선택이 아니라 필수**다. 평문 덤프는 암호화 직후 `shred` 로 폐기한다.

### 구현 방침

- **GitHub Actions**로 매일 운영 DB를 덤프해 보관한다. 기존 `supabase-keepalive.yml`과 같은 자리에 추가한다.
- ⚠️ **덤프 파일 자체가 고객 개인정보다.** 리포지토리가 **public**이므로 절대 리포지토리에 커밋하면 안 된다. 비공개 저장소(GitHub Actions artifact의 보존기간 한계, 또는 별도 오브젝트 스토리지)로 보내고 접근을 제한한다.
- 암호화 컬럼은 암호문 그대로 덤프되지만, **복호화 키는 Supabase Vault에 있다.** 키가 함께 유실되면 덤프가 있어도 복호화할 수 없다 → **Vault 키의 별도 보관 방침도 함께 정해야 한다.**
- 복구 절차를 문서로 남긴다. 덤프만 있고 복구 절차가 없으면 실제 사고 시 쓸 수 없다.
- 보존 주기(며칠치 유지), 실패 시 알림(Slack)을 함께 설계한다.

### 남는 리스크 (인지하고 선택한 것)

- 복구가 **수동**이다. Pro의 대시보드 클릭 복구보다 느리고, 사고 상황에서 사람이 실수할 여지가 있다.
- 백업 시점 사이의 데이터는 유실된다(일 1회면 최대 24시간치).
- 이 백업 잡 자체가 조용히 실패할 수 있으므로 **실패 알림이 필수**다.

## D-07a. 입금 확인 자동화 — 오픈뱅킹 API 방식 🟡

**결정일**: 2026-09-08

### 결정

**회사 계좌 하나를 그대로 쓰고, 거래내역을 API로 조회해 입금을 자동 매칭**한다.
(가상계좌 방식은 채택하지 않음 — 아래 "검토 경위" 참고)

### 검토 경위 (기록)

담당자(Claude)는 **PG사 가상계좌**를 권고했다. 신청자별 전용 계좌번호를 발급하는 방식이라 입금자명 불일치 문제와 미입금 자동취소가 함께 해결되고, 카드 결제를 켜지 않아도 되기 때문이다.
사용자는 단점(입금자명 매칭 문제 잔존, 금융결제원 심사 필요)을 안내받은 상태에서 **오픈뱅킹 방식을 선택**했다. 이 결정을 따른다.

### 확인된 사실 (2026-09-08 조사)

- 금융결제원 오픈뱅킹에 **거래내역조회 API**가 존재한다. 이용기관이 **핀테크이용번호 + Access Token**으로 등록된 계좌의 거래내역을 조회하는 구조다.
- 이용기관 신청은 금융결제원 오픈뱅킹 사이트 회원가입 후 마이페이지에서 서비스별로 신청한다. **심사 절차가 있다.**
- 사업자등록이 완료됐으므로 신청 자격 자체는 갖춰졌다.

### ⚠️ 반드시 해결해야 할 설계 과제

**1. 매칭 키 — 입금액 + 입금자명 (2026-09-08 확정)**

거래내역에는 "입금자명 + 금액 + 시각"만 온다. **금액과 입금자명 둘 다 일치할 때만 자동 확정**한다.

> **검토 경위**: 담당자(Claude)는 초안에서 **금액 끝자리 유니크화**(55,001 / 55,002 …)를 권했다. 이름이 달라도 금액이 고유해 정확히 매칭되기 때문이다.
> 사용자는 이를 **기각**했다 — *"참가자마다 누구는 100,001원이고 누구는 100,002원이라는 건 너무 듣도보도 못한 방식"*. 실제로 고객이 금액을 의심하거나 반올림해 입금하면 오히려 실패율이 올라간다.
> **대신 입금자명을 정확히 입력하도록 UI에서 강하게 안내**하는 방향으로 확정했다.

**필수 UI 조치** (이 방식이 성립하기 위한 전제):
- **신청 폼**의 입금자명 입력란에 강조 문구 — "실제로 입금하실 분의 성함과 **정확히 일치**해야 자동 확인됩니다"
- **신청 완료 화면**에서 입금액과 입금자명을 다시 한 번 강조 노출
- **문자1(신청확인)** 템플릿에도 동일 문구 포함

**그래도 남는 실패 케이스** → 어드민 "미매칭 입금" 화면이 **반드시 필요**하다:
- 동명이인이 같은 인원수로 신청 (같은 금액 + 같은 이름 → 어느 건인지 모호)
- 가족·지인 명의로 입금, 회사명으로 입금
- 은행이 이름 뒤에 부가정보를 붙이는 경우
- 금액 오입력, 중복 입금, 분할 입금

**2. 매칭 실패 / 예외 처리**
자동 매칭이 안 된 입금, 금액이 다른 입금, 중복 입금, 취소 후 재입금은 **사람이 판단해야 한다.** "미매칭 입금 목록" 화면이 어드민에 필요하다 → **D-미정(어드민 범위)** 에 반영할 것.

**3. 조회 주기**
webhook이 아니라 **폴링(주기적 조회)** 이므로 실시간이 아니다. 5~10분 주기로 조회하는 크론이 필요하다. 고객은 입금 후 최대 그만큼 기다린다.
→ 현재 `/api/cron/reminder`가 **외부 크론에 등록되지 않아 자동 실행되지 않는 상태**다. 이 크론 실행 기반부터 제대로 갖춰야 한다.

**4. 30분 미입금 자동취소**
가상계좌와 달리 자동 만료가 없으므로 **직접 구현**해야 한다. (현재는 코드가 없고 운영자 육안 판단)

**5. 대안 검토 여지**
금융결제원 오픈뱅킹 외에 **거래 은행의 기업 OpenAPI**(예: KB 기업OpenAPI)도 자기 계좌 입출금 조회 용도로 쓸 수 있다. 착수 시 **심사 난이도·공수·비용을 비교**해 더 나은 쪽을 택한다.

### 함께 정리할 것

- 입금 계좌를 **개인 명의 → 사업자 명의**로 옮길지 결정 (현재 `src/lib/bankAccount.ts`에 개인 카카오뱅크 계좌 하드코딩).
- 계좌 정보를 코드 하드코딩에서 **설정/DB로** 옮긴다 (계좌가 바뀔 때 배포가 필요하면 안 됨).

| **권한·감사** | 운영자 계정, 역할, **액션 감사로그** |

### 이유

현재 어드민은 "세션 목록 화면 하나 + 상단 버튼 4개"가 전부이고, 회차 등록조차 SQL Editor로 해야 한다. 사용자 평가대로 *"분류·카테고리화가 전혀 안 되어 있고 사업적으로 도움이 되지 않는"* 상태다.

### 구현 시 유의

- **범위는 전체지만 만드는 순서는 나눈다.** 정기 운영을 시작하려면 아래가 먼저 동작해야 한다:
  1. 테마 CRUD → 2. 회차 CRUD → 3. 미매칭 입금 처리 → 4. 전체 신청 목록+검색 → 5. 대시보드 → 6. 나머지
  이 순서로 만들면 4번까지만 되어도 **SQL Editor 없이 매주 운영이 가능**해진다.
- **감사로그는 되돌리기 어려운 액션부터**: 신청 취소, 환불 완료, 수동 등록, 회차 비활성화, 입금 확인.
- **운영자 계정**: 현재는 `ADMIN_PASSWORD` 공유 비밀번호 1개라 "누가 했는지"가 남지 않는다. Supabase Auth + 역할(role) 기반으로 갈지, 어드민 전용 별도 인증을 유지할지는 설계 시 판단. **`admin.wouldyouescape.com` 서브도메인 분리 구조는 유지**한다(잘 되어 있다).
- 공지·FAQ를 DB로 옮길 때 주의: 현재 `FaqSection.tsx`의 FAQ 본문에 **JSX가 섞여 있어** 그대로는 옮길 수 없다. 서식 표현 방식을 먼저 정해야 한다.

리포지토리가 **public으로 유지**되므로, 아래는 규칙이 아니라 **강제 조건**이다.

- ⚠️ **현재 이미 노출된 값**: `src/lib/openYourDreamGateAuth.ts`의 게이트 코드 `"43129573"`. 주석에 "이스터에그 수준 보안이라 하드코딩으로 충분"이라는 판단 근거가 적혀 있으나, **공개 저장소이므로 "실물 명함을 가진 사람만 통과"라는 전제는 성립하지 않는다.** 유지할지 환경변수로 뺄지 별도 판단 필요.
- 신규 기능(오픈뱅킹 인증정보, PG 키, 포인트 정책 등)을 붙일 때 특히 주의한다.
