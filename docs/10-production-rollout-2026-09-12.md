## 4. 데이터 이관 — 전부 md5/digest 대조로 검증

test에서 완성된 콘텐츠를 운영으로 옮기고, **양쪽 해시가 일치하는지 확인**했다.

| 대상 | 검증 결과 |
|---|---|
| 테마 본문 | md5 `efa063aa…` **일치** |
| 장소 · 요금 · 카테고리 | digest 3종 **전부 일치** |
| 문자 포맷 `_v2` 7종 + 쿠폰 | md5 **전부 일치** |
| 공지 5 · FAQ 7 | digest **양쪽 동일** |
| 8/29 신청 58건 | 백업 대조 **무결성 오류 0건** |
| 쿠폰 매핑 | 39명 × (본인 1 + 지인 1) = 78장, 명단 밖 배정 **0건** |

**시드 파일을 그대로 재생하지 않은 이유**: 시드 이후 어드민에서 문구가 여러 번 수정돼(환불 기준 날짜화, 참가 연령 종료시각 기준, 장소안내 이틀 전) 시드를 다시 돌리면 옛 문안이 들어간다. test의 **최종 상태**를 옮기고 해시로 대조하는 방식을 택했다.

**레거시 문자 포맷은 덮어쓰지 않았다**: 운영 쪽이 test보다 최신이었다(카카오톡 채널 링크 포함). 이후 §6에서 별도로 정리.

## 5. ⚠️ 가장 중요한 발견 — 운영에서 신청이 전혀 되지 않고 있었다

마이그레이션 적용·환경변수 점검·스키마 해시 대조를 **모두 통과한 뒤에도** 남아 있던 문제다.

### 증상

운영에서 실제로 신청을 제출하니 실패했다.

```
Could not find the function public.submit_application_v2(
  ..., p_coupon_code, ...) in the schema cache
```

### 원인

| | 운영 | test |
|---|---|---|
| `submit_application_v2` | 파라미터 **9개** (쿠폰 이전) | 파라미터 **10개** |
| `applications.coupon_id` / `discount_krw` | **없음** | 있음 |

앱은 항상 `p_coupon_code`를 포함한 10개로 호출한다. 쿠폰 스키마를 test에서 떠올 때(`p13`) 테이블과 함수 4개만 가져오고 **`applications` 쪽 컬럼과 이 함수를 빠뜨린 것**이 원인이다.

### 조치

`p17`(컬럼) · `p18`(함수)로 반영. 적용 후 `pg_get_functiondef` md5가 test와 **완전 일치**(`ed7d17f9…`)하는 것을 확인했다.

옛 9개짜리 시그니처는 **지우지 않았다**. 호출하는 코드가 없음을 grep으로 확인했지만(호출부는 신규 신청폼 한 곳, 항상 10개 전달), 2026-08-14 함수 오삭제로 서비스가 마비된 이력이 있어 남겨 두고 `_backup/`에도 보관했다.

### 교훈

> **스키마 해시 대조를 통과해도, 실제 사용자 플로우를 끝까지 돌려보지 않으면 잡히지 않는 결함이 있다.**

이 버그는 오직 브라우저로 신청을 제출해봤기 때문에 발견됐다. 발견하지 못했다면 **9/26 오픈 당일 아무도 신청하지 못했을 것**이다.

같은 패턴(test SQL Editor에서 ad-hoc 생성 → 마이그레이션 누락)이 오늘 **두 번** 나왔다(쿠폰 스키마, 이 함수). 작업 종료 시점에 **함수·테이블·뷰·정책·트리거·제약·인덱스·권한 전수 대조**를 수행해 더 이상 미기록 객체가 없음을 확인했다(§8).

## 6. 조용히 망가져 있던 것 3건

셋 다 **아무 에러도 내지 않고 정상인 척하고 있었다.** 이번 작업에서 발견해 전부 "실패가 보이도록" 고쳤다.

### 6-1. `ensure_rls` 이벤트 트리거 — 한 번도 동작한 적 없음

본문이 **존재하지 않는 함수** `pg_event_trigger_table_spec()`를 호출했고, 바로 뒤 `exception when others then null`이 그 오류를 통째로 삼켰다. 새 테이블이 생겨도 RLS가 켜지지 않았고 흔적도 남지 않았다.

**실제 피해는 없었다** — 각 마이그레이션이 `enable row level security`를 직접 적어 왔다. 점검 결과 public 스키마 31개 테이블 **전부 RLS on**.

`pg_event_trigger_ddl_commands()` 기반으로 교체. 예외는 계속 삼키되 `null`이 아니라 **WARNING**으로 남긴다(여기서 예외를 올리면 RLS를 못 켜는 순간 `CREATE TABLE` 자체가 실패해 더 위험하다). 양쪽 DB에서 일회용 테이블로 실제 동작을 확인 후 프로브 삭제. → `p15`

### 6-2. Supabase keepalive — 한 번도 제대로 호출된 적 없음

원인 셋이 겹쳐 있었고, 셋 다 **초록불**로 보고되고 있었다.

1. 운영 URL에 `www`가 빠져 **308 리다이렉트**만 받음 — `curl`에 `-L`이 없어 엔드포인트 미호출
2. test 사이트는 **HTTP 500** — test Vercel 프로젝트 환경변수가 `TEST_CRON_SECRET`인데 코드는 `CRON_SECRET`을 읽음
3. `curl`은 401/500을 받아도 **종료코드가 0** — 상태 코드 미검사로 위 둘이 전부 성공 처리

정규 URL 사용 + HTTP 200 검사 + 실패 시 Slack 알림 + `workflow_dispatch` 추가로 수정. 현재 **운영·test 모두 `200 {"ok":true}`**.

> Supabase Free 플랜은 7일 무활동 시 프로젝트를 자동 정지한다. 운영은 실사용 트래픽이 있어 무사했지만 **test는 위험한 상태였다.**

### 6-3. 장소안내 문자 크론 — 하루 1회로 바꾸면 "이틀 전"이 "하루 전"이 됨

라우트가 "지금부터 48시간" 창을 쓰고 있어 오전 10시 실행과 회차 시각(11:30/15:30/19:30)이 어긋났다.

| 실행 | 48시간 창 | 9/26 11:30 회차 |
|---|---|---|
| 9/24(목) 10:00 | ~ 토 10:00 | ❌ 1시간 30분 차이로 누락 |
| 9/25(금) 10:00 | ~ 일 10:00 | ✅ → **하루 전 발송** |

창을 **날짜 기준**("KST 오늘+2일의 하루 끝까지")으로 교체. 환불 규정도 `p6`에서 시각→날짜 기준으로 바뀌었으므로 일관된다. 연말 경계(12/31 → 1/2) 포함해 계산을 검증했다.

하한은 `now()`로 남겨 **하루 실행이 누락돼도 다음 날이 놓친 회차를 잡는다**(하루 전 안내가 되긴 하지만 아예 못 받는 것보다 낫다).

## 7. 기능 변경 (운영 반영됨)

### 7-1. 문자 발송을 일괄 전송으로 — 왕복 N회 → 1회

솔라피 SDK의 `send()`는 원래 배열을 받는다(한 요청 최대 10,000건). 그런데 세 곳 모두 한 명씩 보내고 있었다.

| 경로 | 인원 | 이전 | 이후 |
|---|---|---|---|
| 문자3 장소안내 | 회차당 최대 40 | 솔라피 40회 + DB 조회 40 + 쓰기 40 | **1회** + 1 + 1 |
| 쿠폰 발송 | 37 | 솔라피 37회 | **1회** |
| 문자7 회차취소 | 확정+대기 전원 | N회 + 조회 2N + 쓰기 N | **1회** + 1 + 1 |

부분 실패를 되짚을 수 있도록 `sendSmsBulk()`가 호출부의 **key**(신청 id / 참여자 id)로 결과를 돌려주고, 응답의 `failedMessageList`(수신번호 기준)를 매핑한다. 실패한 사람만 다음 실행에서 재시도된다.

판단이 갈리는 두 지점:
- **응답 형태가 예상과 다르면 전부 성공으로 간주** — SDK는 전건 실패 시 예외를 던지므로, 예외 없이 돌아온 건 접수됐다는 뜻이다. 여기서 실패로 잡으면 중복 발송이 된다.
- **예외가 나면 전부 실패로 간주** — 기존 한 건씩 보내던 코드와 같은 판단(못 받는 것보다 한 번 더 받는 쪽이 낫다).

쿠폰은 **배정(`assign_coupon`)을 한 명씩 그대로 뒀다.** 되돌릴 수 없는 작업이라 건별 확인이 필요하다. 묶은 것은 발송뿐이다.

**실물 검증 완료**: 한 그룹에 2건, `registeredSuccess: 2`, 과금 1회, `failedMessageList` 배열 확인.

### 7-2. 장소안내를 동행자 전원에게

기존에는 신청 건의 **대표 1명**에게만 갔다. 장소는 당일 필수 정보라 전원 발송으로 변경.

발송 표시도 참여자 단위(`application_attendees.reminder_sms_sent_at`)로 내렸다. 신청 단위로 두면 4명 중 1명만 실패했을 때 **그 사람을 영영 못 보내거나 4명 전원에게 다시 보내게** 된다.

`service_role`은 `application_attendees`에 테이블 권한이 없으므로(의도된 잠금) `mark_attendee_reminder_sent()` SECURITY DEFINER 함수를 통한다. 기존 발송 이력 39명분을 백필해 **재발송 대상 0명**임을 확인했다. → `p16`

### 7-3. 그 외

- **롤링 오픈**: 회차마다 `opens_at`을 미리 박아 시간이 지나면 저절로 열린다(크론 실행에 의존하지 않음). 요일 고정 없이 각 회차의 정확히 3주 전.
- **취소 시 닉네임 반환**: `unique(session_id, nickname)` 제약을 트리거로 교체. 상태가 다른 테이블에 있어 부분 인덱스로는 표현 불가.
- **약관 v1.2**: 참가 연령을 회차 **종료 시각** 기준으로(22:00 전 만 16세 / 후 만 19세), 환불 기준 날짜·시각 명시.
- **UI**: 홈 `Planets to Escape` 지그재그 배치 + 자전 행성, contents 포스터 카드, 잠긴 테마 자물쇠·클릭 차단, 헤더 `PRE-OPEN` 배지 제거.

## 8. 작업 종료 시점 test ↔ 운영 전수 대조

§5의 사고가 재발하지 않도록 마지막에 전 객체를 대조했다.

| 대상 | 결과 |
|---|---|
| 함수 30개(공통) | **로직 차이 0건** |
| 테이블 25 / 컬럼 | 24개 md5 완전 일치 |
| 뷰 9 · RLS 정책 12 · 트리거 2 | **전부 일치** |

**차이났지만 정상인 것**

- `get_pii_key`, `hash_phone` — Vault 키가 환경별로 **달라야** 정상
- `lookup_application_v2`, `v3` — **주석만** 다름(주석 제거 후 md5 일치)
- `decrypt_pii`/`encrypt_pii` — 파라미터 **이름**만 다름
- test에만 있는 함수 5개 + `profiles` 컬럼·제약·인덱스 — 휴면 처리된 회원제 잔재

**`anon` 권한 점검**: SELECT가 열린 것은 공개돼야 할 9개뿐(`themes`, `sessions`, `session_view`, `theme_categories`, `theme_price_tiers`, `theme_public_venue`, `venue_public`, `notices`, `faqs`). `applications`·`application_attendees`·`coupons`·`session_venues`·`sms_templates`·`venues`·`admin_*` 뷰는 SELECT 없음(붙어 있는 `REFERENCES/TRIGGER/TRUNCATE`는 Postgres 기본값이라 데이터를 읽지 못한다).

## 9. 운영에서 실제로 돌린 검증

문서·해시 대조로는 잡히지 않는 것을 확인하기 위해 **운영에서 실 플로우를 끝까지** 돌렸다.

| 단계 | 결과 |
|---|---|
| contents 잠금 카드 | `DIV`(링크 아님), `href` 없음, **키보드 포커스 불가** |
| 달력 | 9/26·27만 선택 가능 (롤링 오픈 규칙대로) |
| 회차별 연령 | "만 19세 이상만 참여할 수 있어요" / 동의 문구도 연동 |
| 전화번호 검증 | placeholder를 값으로 오인하지 않고 정확히 거부 |
| **쿠폰 적용** | 68,000 → **−5,000 → 63,000원** |
| 신청 완료 | 접수번호 발급 + 문자 발송 |
| DB 저장 | `discount_krw` · `amount_krw` · `coupon_id` · `used_at` 정상 |
| `/lookup` 조회 | 할인 전 / 할인 / 결제액 분리 표시 |
| 쿠폰 문자 | LMS 1건, 미치환 변수 0개, 실패 0건 |

**검증용으로 만든 데이터는 전부 원복했다** — 테스트 신청 삭제(신청 58건 복귀), 쿠폰 사용 해제(배정은 유지).
