## 1. 매주 주말 정기 운영으로 전환

### 지금
- 회차는 `sessions` 테이블에 **SQL Editor로 직접 INSERT**. 어드민 UI 없음.
- `slug`는 사람이 손으로 짓는다 (`0829-meeting`).
- `slot`은 CHECK로 `'afternoon' | 'evening'` **2개 고정**.
- `event_date` + `start_at`/`end_at`을 각각 따로 넣어야 하고 정합성 보장 장치가 없다.
- 반복(recurrence) 개념이 전혀 없다.

### 걸림돌

| 항목 | 위치 |
|---|---|
| 회차 등록 UI 부재 | 어드민 전체 |
| 회차 상세 화면의 타임테이블이 코드 상수 | `sessions/[slug]/page.tsx` `schedule` (13:00/19:00 고정) |

| 전날안내 문자 자동화 없음 | `/api/cron/reminder` 미등록 |
| 장소 주소가 `sms.ts`에 하드코딩 | `src/lib/sms.ts` 2곳 (`session_venues.venue_address` 컬럼은 있는데 안 씀) |

### 결정해야 할 것
- **회차 생성 방식**: 어드민에서 1건씩 생성 / 템플릿 기반 반복 생성(매주 토·일 자동 생성) / 둘 다?
- **`slug` 규칙**: 자동 생성(`{테마}-{YYYYMMDD}-{슬롯}`)으로 갈 것인가. 기존 `0829-*` URL의 영구 리다이렉트 필요 여부.
- **`slot`을 계속 열거형으로 둘 것인가**, 아니면 `start_at`만으로 충분한가 (주말 3회차 이상 운영 가능성).
- **과거 회차 처리**: 종료된 회차를 `/contents`에서 어떻게 보여줄 것인가 (숨김 / 지난 회차 아카이브 / 후기 연결).

## 2. 범용화 — 관리자에서 방탈출 테마 추가 등록

### 지금
테마에 해당하는 **엔티티가 DB에 없다.** `sessions.theme_name`(문자열)과 `difficulty`(1~5)만 있고, 테마를 설명하는 나머지는 전부 코드 상수다.

`src/app/(site)/sessions/[slug]/page.tsx` 한 파일에 박혀 있는 것:

```
DATING_FOR_YOU_CARDS / GROUP_FOR_YOU_CARDS   ← "이런 분께 추천" 4종
contentSteps                                  ← 진행 3단계 설명
schedule                                      ← 타임테이블 (시각 포함)
precautions                                   ← 주의사항
themeAccentColor                              ← 테마 강조색 (#ff5ec4 / #3dffb0)
```

즉 **새 테마를 추가하려면 지금은 코드를 고치고 배포해야 한다.**

### 필요한 것
"테마"를 데이터로 승격 — 이름, 설명/스토리, 난이도, 소요시간, 대표 이미지·갤러리, 진행 단계, 타임테이블, 주의사항, 추천 대상, 강조색, 기본 가격·정원.

**이미 성공한 선례가 있다**: `sms_templates` 테이블 + `/admin/sms-templates` 편집기 = "코드 배포 없이 운영자가 문구를 바꾼다". 이 패턴을 테마/공지/FAQ로 확장하는 게 자연스럽다.

### 결정해야 할 것
- **테마 콘텐츠의 저장 형태**: 정규화된 컬럼 / JSONB 블록 / 블록 에디터. 운영자가 직접 편집할 범위는 어디까지인가.
- **이미지 관리**: Supabase Storage 도입 여부 (현재 `public/`에 정적 파일로만 존재, 업로드 경로 없음).
- **테마 ↔ 회차 관계**: 회차가 테마의 기본값(가격·정원·소요시간)을 상속하고 회차별로 덮어쓸 수 있게 할 것인가.
- **공지/FAQ도 DB로 옮길 것인가** (지금은 `NoticeSection.tsx` / `FaqSection.tsx` 하드코딩, FAQ 본문에 JSX가 섞여 있어 그대로는 DB로 못 옮긴다).

## 3. 소개팅 버전 제거 · 카테고리 제거

### 영향 범위 (실측)

**프론트**: `'소개팅'` 참조 파일 **19개**, `isDatingTheme()` 호출 **37곳**

주요 지점: `sessions/[slug]/page.tsx`(대상카드·진행단계·타임테이블·색상 분기), `apply/actions.ts`, `ApplyNotices.tsx`, `capacityBadge.ts`, `sms.ts`, `slack.ts`, `eligibility.ts`, `FaqSection.tsx`, `NoticeSection.tsx`, `terms/page.tsx`, `about/page.tsx`, `layout.tsx`(SEO 키워드), `review-guide`, 어드민 3화면

**DB**:
- `sessions.session_type` CHECK `('그룹','소개팅')`
- 성별 정원 컬럼 6개: `capacity_confirm_line_male/female`, `capacity_max_male/female`, `male_closed`, `female_closed`
- `submit_application()` 내 `session_type = '소개팅'` 분기 **8곳** (1인 강제, 성별 필수, 출생년도 범위, 정원 판정, 마감 처리, 대기순번)
- `get_session_stats()` 성별 카운트 6개
- `sms_templates`의 `event_reminder_dating`
- `sponsorship_dating_applications` 테이블 + `submit_sponsorship_dating_application()` + `admin_sponsorship_dating_applications_view` + `/dating-sponsorship-guide` 페이지

**데이터**: 소개팅 회차에 **확정 20건 / 대기 1건 / 취소 13건 = 실고객 34건**이 남아 있다.

### 결정해야 할 것
- **성별(`gender`) 필드를 남길 것인가.** 지금 소개팅 때문에 전 테마 필수인데, 소개팅이 사라지면 수집 근거가 약해진다. (개인정보 최소수집 원칙) — 통계 목적으로 남길지, 선택 입력으로 낮출지, 제거할지.
- **소개팅 이력 처리**: 컬럼/테이블 삭제 vs 보존 후 UI에서만 제거 vs 아카이브 스키마로 이관. **삭제는 되돌릴 수 없다** — `CLAUDE.md`의 2026-08-14 장애 교훈 그대로 적용 대상.
- **"카테고리 제거" 후에도 회차 구분자가 필요한가** — 테마가 늘어나면 결국 목록/필터가 필요해진다. `session_type`을 없애되 `theme_id`가 그 역할을 대체하는 형태가 자연스럽다.
- **크로스테마 배타(`content_group`) 규칙을 유지할 것인가.** 원래는 "같은 컨텐츠는 1건만"이었는데, 테마가 늘고 매주 열리면 "한 사람이 여러 주에 여러 번 참여"가 정상 시나리오가 된다. **현행 규칙 그대로면 재참여가 영구 차단된다** — 반드시 재정의해야 할 항목.
- 소개팅 협찬 페이지/파이프라인도 함께 정리할 것인가.

## 4. 나이 제한 → 만 14세 이상만

### 지금
```
DB:  application_attendees.birth_year CHECK between 1987 and 2007
     submit_application() — 소개팅 1990~2001 / 그룹 1987~2007 이중 분기
코드: src/lib/eligibility.ts (상수 4개 + 헬퍼 3개)
UI:  신청 폼 안내 문구, /sessions/[slug] 주의사항, 약관
```

### ⚠️ 핵심 제약: **생년월일이 아니라 출생연도만 수집한다**

"만 14세"는 생일이 지났는지에 따라 갈리는데, `birth_year`만으로는 정확히 계산할 수 없다.

세 가지 선택지:

| 선택 | 규칙 | 성격 |
|---|---|---|
| (a) 보수적 연도 규칙 | `birth_year <= 올해 - 15` | 만 14세가 확실한 사람만 통과. 만 14세 생일이 지난 일부를 배제 |
| (b) 느슨한 연도 규칙 | `birth_year <= 올해 - 14` | 아직 만 13세인 사람이 통과할 수 있음 — **법적 목적이라면 부적절** |
| (c) 생년월일 수집으로 변경 | `birth_date` 도입 | 정확하지만 수집 항목 증가 + 스키마·폼·암호화 변경 |

법적 리스크 회피가 목적이라면 (a) 또는 (c). **이건 사업 판단이 필요한 지점이다.**

### 부수 결정
- **상한(`birth_year >= 1987`)은 완전히 제거하는가.** "만 14세 제한만 두기"는 상한 없음을 뜻하는 것으로 읽히지만 명시 확인 필요.
- **음주 정책**: 현재 소개팅 2부에만 음주 제공(BYOB 허용). 소개팅이 사라지면 음주도 함께 사라지는가? 만약 남는다면 **만 14세와 음주는 양립 불가**이므로 회차별 연령 제한 오버라이드가 필요하다.
- **DB 변경 순서**: CLAUDE.md v40 기록의 교훈대로 — **CHECK 제약을 먼저 넓히고 함수를 나중에 교체**해야 한다(반대 순서면 넓어진 함수가 좁은 제약에 막히는 순간이 생긴다).
- 만 14세 미만 차단은 **회차별로 다를 수 있는 값**인가, 사이트 전역 상수인가.

## 5. 로그인 부활 + 비회원 신청 병행

### 이미 있는 자산
- 화면·라우트 일습: `/login`, `/signup`(3단계), `/account`, `/auth/callback`, 카카오·네이버 OAuth 라우트, 계정 연결(`confirm-link`/`cancel-link`)
- 라이브러리: `src/lib/{kakao,naver,profile,oauthLink,accountLookup,age,loginRateLimit}.ts`
- DB: `profiles`, `kakao_links`, `naver_links` (전부 0행, 본인 RLS 정책 적용됨)
- Supabase: **email + kakao provider가 이미 켜져 있고 회원가입도 막혀 있지 않다**
- 이메일 발송: Resend 커스텀 SMTP 연결 (CLAUDE.md 기록, 이번 미확인)

### 결정적 갭
**`applications`에 `user_id`가 없다.** 계정과 신청을 잇는 연결고리가 아예 존재하지 않는다.
현재 사람을 식별하는 유일한 키는 `application_attendees.phone_hash`(HMAC)다.

### 결정해야 할 것
- **정체성(identity) 모델**: 계정 로그인 시에도 `phone_hash`를 정체성의 축으로 유지할 것인가, `user_id`를 축으로 옮길 것인가. 둘의 불일치(계정 이메일은 같은데 전화번호가 다른 경우 등) 처리 규칙.
- **비회원 신청의 사후 귀속**: 로그인 후 "내 전화번호로 된 과거 신청"을 계정에 자동 연결할 것인가. 자동이면 **전화번호만 알면 남의 신청을 가져갈 수 있는 위험**이 생긴다 → 인증 수단 필요(현행 접수번호 조합 / SMS OTP).
- **로그인의 실익 정의**: 재신청 시 정보 자동입력 / 참여 이력 / 리뷰 / 포인트·단골 혜택 / 추천인. 실익이 없으면 로그인은 이탈 요인만 된다.
- **네이버 OIDC 재확인**: CLAUDE.md에 "네이버가 표준 OIDC 지원을 시작한 걸 확인함"이라고 기록돼 있다. 착수 시 `https://nid.naver.com/.well-known/openid-configuration`을 다시 조회해 현행 확인할 것 — 자체 OAuth 라우트 대신 Supabase Custom OIDC로 단순화할 수 있다.
- **`disable_signup`**: 부활 전까지 `true`로 닫아둘 것인가 (04-C-B 참고).
- **PII 암호화와 계정의 관계**: `profiles`는 평문(`name`, `phone`, `birth_date`), `application_attendees`는 암호화. **두 저장 방식이 공존한다.** 통일 필요.

| **권한/감사** | 공유 비밀번호 1개 | 계정별 로그인, 역할, 액션 로그 |

### 결정해야 할 것
- **운영자 계정 도입 여부.** 도입하면 Supabase Auth + `role` 기반으로 갈 것인가, 어드민 전용 별도 인증을 유지할 것인가. (`admin.` 서브도메인 분리 구조는 유지 가치가 높다.)
- **감사 로그 도입 여부와 범위** (취소·환불·수동등록·회차비활성화는 최소 대상).
- **"주문(신청)"을 회차 종속에서 독립시킬 것인가** — 지금은 `/admin/sessions/[id]` 안에서만 신청을 볼 수 있다. 회차가 매주 쌓이면 전체 주문 리스트가 필수가 된다.
- **어디까지를 1차 범위로 할 것인가.** 위 표를 전부 만들면 과대설계다. 정기 운영 개시에 반드시 필요한 최소 집합은 아마 **테마 CRUD + 회차 CRUD + 주문 목록/검색 + 대시보드 처리대기 + 매출 요약**.
